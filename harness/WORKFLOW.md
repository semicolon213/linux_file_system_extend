# 작업 흐름

역할, 작업 분배, 독립 QA, 실패 처리, worktree 규칙, 양식. 필수 규칙(역할 분담, 커밋, WSL 실행, 금지 사항, 디자인 권한)은 AGENTS.md에 있고 여기서 다시 적지 않는다.

## 1. 역할과 권한

| 역할 | 담당 | 책임 | 금지 |
|---|---|---|---|
| Coordinator | Claude 메인 세션 (Orca 운영자) | 작업 분해, 의존성·파일 소유권 관리, 배정, 리뷰, 병합, 상태 확정 | 검증 우회 |
| Architect | Coordinator가 지정 | 요구사항과 기존 계약을 읽고 모듈 책임, 공개 API, 메모리 소유권, 오류·스레드 규칙을 정의. 변경 결정은 ADR(docs/adr/)로 남김 | 무단 구현 |
| Implementer | Codex | 할당 작업과 허용 파일 확인, 기준 테스트 후 최소 범위로 구현, 정상·실패·경계 테스트 작성, 게이트 실행 후 인수인계 제출. 문서 수정도 맡음 | 자체 QA 승인·병합 |
| QA | 별도 Claude 세션 | 지정 SHA의 diff와 계약을 구현자 주장에 기대지 않고 독립 확인. docs/TESTING.md §3 체크리스트와 harness/EVALS.md 적용, 재현 증거와 판정 제출 | 범위를 넘는 구현 수정(국소 수정 예외는 §4) |
| Integration | Coordinator | QA PASS SHA와 승인 범위 확인, 통합 충돌 보고, 적용 가능한 게이트 전체 실행. 실패하면 병합 완료로 기록하지 않음 | 실패 상태 병합 |
| UI Reviewer | QA 세션 | 화면 캡처, 키보드·상태 검증 | 임의 디자인 변경 |

사람(사용자)이 최종 범위 변경, 위험 작업, 릴리스를 승인한다.

## 2. 상태 흐름

BACKLOG → READY → IN_PROGRESS → VERIFY → QA → APPROVED → MERGED. 실패 시 REWORK, 선행 조건 부족 시 BLOCKED.

- READY는 선행 계약이 있는 작업만 받는다. Coordinator가 공통 파일 소유권을 배정하고 READY 작업만 배포한다.
- VERIFY는 구현과 개발자 게이트가 끝나고 독립 QA를 기다리는 상태다. 독립 QA는 큰 단위(R1 전체)로 묶어 하므로 VERIFY 작업이 기준 브랜치에 먼저 병합될 수 있다. 이때도 묶음 QA PASS 전에는 APPROVED로 올리지 않는다.
- QA 이후 코드가 바뀌면 기존 승인은 무효다. 작업 상태는 Coordinator만 확정하고 harness/TASKS.md와 harness/PROGRESS.md를 갱신한다.

## 3. 작업 순서

1. Coordinator가 `git status`, 현재 브랜치, AGENTS.md "작업별 참조 문서", 관련 요구사항과 작업 지시서를 확인한다.
2. Coordinator가 Codex에 작업을 전달한다. 전달 내용: 작업 목표와 요구사항 ID, 읽어야 할 문서와 선행 작업, 수정 가능한 파일과 금지 범위, 지켜야 할 인터페이스와 제약 사항, 완료 조건과 검증 명령, 보고 형식과 인수인계 대상.
3. Codex는 기준 커밋과 테스트 결과를 기록하고 전용 worktree(§6)에서 구현한다. 구현과 개발자 검증 뒤 §7 인수인계 양식으로 변경 파일, 주요 판단, 실행한 명령과 종료 코드, 남은 위험을 보고한다.
4. Coordinator는 변경 파일, 실제 diff, 실행한 테스트, 종료 코드, 남은 위험을 직접 확인한다. 보고만으로 완료 처리하지 않는다.
5. 묶음 단위(R1 등)가 끝나면 Coordinator가 구현에 참여하지 않은 별도 Claude 세션에 독립 QA를 요청한다. QA 세션은 실제 diff와 요구사항을 비교하고 필요한 테스트를 직접 실행한다. FAIL이면 재현 근거와 함께 반환한다.
6. 문제는 §4 기준으로 수정 담당을 정하고, 수정 뒤 별도 QA 세션이 관련 검증을 다시 실행한다. 모든 품질 게이트(docs/TESTING.md §1)를 통과해야 완료다.
7. Integration은 승인된 SHA만 통합하고 전체 회귀 검사를 수행한다. 통합 성공 후 harness/PROGRESS.md(추적표 포함)를 갱신한다.

## 4. QA 수정 처리

- 아키텍처, 공개 인터페이스, DB 스키마, 빌드·의존성, 여러 모듈의 동작, 비단순 로직에 영향을 주는 수정은 Codex에 돌려보낸다. Coordinator가 실패 증거와 완료 조건을 보완해 다시 전달한다.
- 오탈자, 문서, 서식, 계약을 바꾸지 않는 명백한 국소 수정은 QA 세션이 직접 고칠 수 있다. 이 경우에도 관련 테스트를 다시 실행하고 결과를 기록한다.
- 크기가 애매하거나 회귀 위험을 판단하기 어려우면 큰 수정으로 보고 Codex에 반환한다.
- Codex가 큰 수정을 마치면 새 결과를 기준으로 독립 QA를 반복한다.

## 5. 실패 처리

실패 시 명령, 종료 코드, 로그, SHA, 환경, 재현 절차를 기록한다. 기존 실패와 신규 실패를 구분하되 기존 실패도 숨기지 않는다. 동일 원인 수정 시도는 2회까지 진행하고 해결되지 않으면 BLOCKED로 반환한다. 권한 부족, 계약 부재, 데이터 손실 위험은 즉시 중단한다. 테스트 완화나 위험 명령으로 우회하지 않는다. QA FAIL은 수정 후 관련 게이트 전체를 다시 실행한다.

## 6. Worktree 규칙

- 기준 브랜치는 실제 존재하는 커밋이어야 한다. `git rev-parse --verify refs/heads/main`으로 확인하고 main이 없으면 Coordinator가 실제 기준 브랜치를 지정한다. 최초 커밋 없는 저장소는 초기화 후 작업한다.
- 작업별 `feature/<task-id>-<name>` 브랜치와 독립 worktree를 사용한다. 예: `git worktree add -b feature/mon-001-watcher ../fs-mon-001 main`.
- 작업별 허용 경로를 명시하고 공통 헤더·CMake·migration은 단일 소유자가 관리한다(docs/ARCHITECTURE.md §3, ADR-0004). 빌드 디렉터리와 테스트 DB를 worktree별로 분리한다.
- 다른 worktree 수정, 강제 삭제, `reset --hard` 금지. 병합 전 기준 브랜치 변경을 확인하고 충돌은 Coordinator에게 보고한다. 병합 및 검증 후 깨끗한 worktree만 제거한다.
