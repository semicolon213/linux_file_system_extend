# ADR-0006 루트 크기 색인과 변경량 1분봉

상태: 제안 (2026-11-24, 사용자 요구 PRODUCT.md "변경량 1분봉", R1)

## 맥락
1분봉은 감시 루트 총용량의 분 안 시·고·저·종이 필요하고, 목록 변동 열(U-4)은 직전 이벤트 대비 크기 증감이 필요하다. 삭제된 파일은 다시 stat할 수 없으므로 삭제 직전 크기를 누군가 기억해야 한다.

## 결정
1. mon이 루트별 크기 색인을 재귀 등록·재탐색 순회에서 함께 만든다. 저장 구조는 경로 전체 키가 아니라 감시 디렉터리 노드(이미 registry에 있음)마다 `이름 → 크기` 표다.
2. mon이 이벤트마다 `size_delta`(직전 색인 대비)와 `root_total`(적용 직후 루트 총용량)을 싣는다. 미상이면 known=FALSE. 같은 루트 이벤트 순서대로 `root_total[n] = root_total[n-1] + size_delta[n]`.
3. 루트 총용량은 FsWatchInfo와 `fs_mon_watcher_get_root_total()`로 조회한다.
4. 봉 집계는 새 `dash` 모듈(GTK 없음)이 이벤트의 root_total로 이벤트 단위 고가·저가를 계산한다. 거래량은 정규화 이벤트의 CREATE·MODIFY·DELETE 수.
5. 크기는 st_size(논리 크기), 정규 파일만. 하드 링크는 경로마다 집계(E-7).

## 요청안(경로→크기 표)보다 나은 점
- 경로 전체를 키로 하면 디렉터리 rename 한 번에 하위 키를 모두 다시 써야 하고(10만 파일이면 10만 건), 경로 문자열 중복으로 메모리가 2~4배 든다. 디렉터리 노드별 이름 표는 rename이 O(1)이고 registry의 wd→디렉터리 노드를 그대로 재사용한다.
- 이벤트에 size_delta만 실으면 소비자가 총용량을 누적해야 하고 미상 이벤트 하나로 이후 값이 모두 틀어진다. root_total을 함께 실으면 소비자는 누적 없이 정확한 값을 받고, 미상 구간 뒤에도 다음 known 값에서 바로 회복한다. 별도 조회 API를 주기적으로 부르는 방식은 분 안 극값(고·저)을 놓친다.

## 검토한 대안
- ui가 이벤트마다 파일을 stat: 메인 스레드 I/O, 삭제 파일 크기를 알 수 없음, 열린 폴더만 알 수 있어 루트 총용량을 못 구함.
- dash가 주기적으로 du 순회: 10만 파일에서 비용이 크고 분 안 극값을 놓침.
- st_blocks(할당 크기): 시안과 PRODUCT.md가 파일 크기(KB 증감)로 설명하고 목록 크기 열도 st_size라 일관성을 위해 제외.
- 1분봉을 ui에 둠: 새 창 차트와 공유가 어렵고 GTK 없이 테스트할 수 없음.

## 결과
- mon 메모리 예산: 10만 파일 색인+registry 16MiB 이하(MEMORY_MANAGEMENT §4), G8에서 측정.
- 루트 등록 시 파일마다 fstatat가 추가된다. 1만 파일 등록 시간을 R1-T04 G8에서 기록한다.
- FsEvent에 필드 4개(size_delta/known, root_total/known)와 getter가 추가된다. core(R1-T01) 반영이 필요하다.
